# Step 14 — Security and recovery candidate

- Pairing/connection origin validation: remote HTTPS/WSS only, explicit loopback HTTP for development, no credentials, suffix path/query/fragment or malformed ports. Pairing HTTP redirects refused, response size bounded; existing DPAPI-protected token persistence remains. WebSocket library redirect behavior needs independent review; no claim of transport signing or complete credential isolation.
- Relay regards a device as online only after application hello/welcome, ignores pre-hello messages, persists dispatch intent before send, never automatically re-dispatches a command with prior dispatch intent. Network ambiguity is a cancelled/unverified outcome requiring manual inspection. Startup cancels previously dispatched and orphan automation commands; operator startup cancels outstanding child commands before marking prior runs interrupted.
- Permission narrowing closes outstanding affected commands while controller cancels current/queued work and invalidates attachment preview. Recheck actual reported and enabled capabilities immediately before dispatch. Emergency Stop cancels operator tasks, open commands and pending dialogues; relay pause is not guaranteed physical input reversal, and earlier actions may have happened.
- Existing backup validation, recovery and updater checks preserve data. Full independent live backup restore, version retention, cross-instance consistency, account privacy review, unsigned installer trust and real PC acceptance remain release gates. Tests added for transport and revoke. No production deployment or new paid service.
